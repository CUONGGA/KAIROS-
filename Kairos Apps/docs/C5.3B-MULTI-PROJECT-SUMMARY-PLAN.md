# C.5.3b — Kế hoạch Multi-project Grounded Summary

- **Trạng thái:** Đã triển khai ngày 2026-10-27
- **Phụ thuộc:** C.5.1, C.5.2 và C.5.3
- **Liên quan tiếp theo:** C.5.4b validated audit snapshot

## 0. Kết quả triển khai

- Context/output schema đã tăng lên `kairos.summary_context@2` và `kairos.summary_output@2`.
- Context giữ evidence index nội bộ `E-ref → project → event_id`; `event_id` không được gửi provider.
- Deduplication đã đưa project vào signature và selection đã round-robin deterministic theo project.
- Output bắt buộc chứa mỗi project được chọn đúng một lần; evidence phải thuộc cùng project với claim.
- Markdown và fallback đều render theo project; invalid output chỉ repair một lần rồi fallback.
- Default `summary_output_max_chars` cho site mới là 4.000; site local đã được nâng từ 1.200 lên 4.000.
- HTTP E2E bao phủ cả ba endpoint ingest/timeline/summary, gồm multi-project, batch duplicate atomic,
  required parameters, cache/force và cross-project fallback.
- Verification cuối: 59 test trên 11 module pass sau `migrate` và `clear-cache`.

## 1. Vấn đề trước triển khai

Context Builder trước đây gửi `project` trong từng Event, nhưng contract `kairos.summary_output@1` chỉ có
ba nhóm toàn cục `done`, `in_progress`, `risks_or_notes`. `SummaryClaim` chỉ giữ `text` và
`evidence`; validator chỉ kiểm tra E-ref có tồn tại, không kiểm tra E-ref thuộc project nào. Renderer
vì vậy chỉ nhóm theo trạng thái và không bảo đảm report hiển thị project.

Với một ngày có nhiều project, hiện trạng cũ có các rủi ro:

- Project nhiều Event có thể chiếm phần lớn context vì selection chưa cân bằng theo project.
- Hai Event cùng source/kind/title trong hai project có thể bị deduplicate nhầm vì chữ ký chưa chứa
  `project`.
- Một claim có thể trộn evidence của nhiều project nhưng vẫn qua validator.
- Day Report chỉ lưu E-ref trong Markdown, chưa lưu mapping `E-ref → event_id → project`, nên chưa
  audit được sau generation.
- `summary_output_max_chars=1200` có thể không đủ cho report khoảng mười project.

Mục tiêu C.5.3b là tạo summary được nhóm theo project, kiểm tra chéo project/evidence và bảo đảm mỗi
project được đại diện công bằng trong context khi budget cho phép. C.5.3b chỉ giữ evidence index trong
bộ nhớ để validate; lưu snapshot lâu dài vẫn thuộc C.5.4b.

## 3. Work package đã triển khai

### 3.1 Output model và schema version

Trong `kairos/summary_output.py`:

- Tăng `SUMMARY_OUTPUT_SCHEMA_VERSION` từ `kairos.summary_output@1` lên
  `kairos.summary_output@2`.
- Thêm `ProjectSummary(project, done, in_progress, risks_or_notes)`.
- Đổi `StructuredSummary` thành `projects + omissions`.
- Chỉ chấp nhận chính xác các key của contract; reject field thừa hoặc thiếu.
- Giữ giới hạn claim, omission và tổng số ký tự sau render.

Mô hình nội bộ dự kiến:

```python
@dataclass(frozen=True)
class ProjectSummary:
    project: str
    done: tuple[SummaryClaim, ...]
    in_progress: tuple[SummaryClaim, ...]
    risks_or_notes: tuple[SummaryClaim, ...]


@dataclass(frozen=True)
class StructuredSummary:
    projects: tuple[ProjectSummary, ...]
    omissions: tuple[str, ...]
```

### 3.2 Evidence index phía server

Trong `kairos/llm_context.py`, bổ sung evidence index không gửi tới provider:

```python
@dataclass(frozen=True)
class EvidenceRef:
    ref: str
    project: str
    event_id: str
```

`SummaryContext` bổ sung:

```python
evidence_index: dict[str, EvidenceRef]
project_event_counts: dict[str, int]
selected_project_counts: dict[str, int]
```

Ví dụ index:

```python
{
    "E001": EvidenceRef(ref="E001", project="Kairos Apps", event_id="codex:..."),
    "E010": EvidenceRef(ref="E010", project="Gasco-Platform", event_id="codex:..."),
}
```

`event_id` chỉ tồn tại phía server. Provider chỉ thấy E-ref ngắn và project đã sanitize.

### 3.3 Chuẩn hóa project

Áp dụng policy deterministic trước deduplication và selection:

```python
project = " ".join(str(value or "").split())
project = project[:80]
project = project or "Không xác định"
```

- Không để project rỗng.
- Không để LLM tự suy đoán project.
- Không tự gộp tên gần giống nhau trong C.5.3b.
- Tên như `System32` hoặc thư mục user phải được sửa ở collector/project mapping riêng nếu không phải
  project thật.

### 3.4 Deduplication theo project

Chữ ký deduplication phải đổi từ `source + kind + title` thành:

```python
signature = (
    candidate.project.casefold(),
    candidate.source.casefold(),
    candidate.kind.casefold(),
    normalized_title,
)
```

Hai Event cùng title nhưng khác project phải được giữ độc lập.

### 3.5 Selection cân bằng project

Thay selection tuyến tính bằng policy deterministic theo project:

1. Sanitize và loại Event không đủ điều kiện.
2. Deduplicate riêng trong từng project.
3. Sắp Event trong mỗi project: `error/agent_run` trước, sau đó `occurred_at`, `event_id`.
4. Chọn vòng đầu tối thiểu một Event cho mỗi project nếu budget cho phép.
5. Tiếp tục round-robin giữa các project đến khi chạm `max_events` hoặc `max_chars`.
6. Sắp Event đã chọn theo thời gian trước khi gán `E001...` để output ổn định.

Context envelope bổ sung metadata:

```json
{
  "meta": {
    "source_project_count": 10,
    "selected_project_count": 10,
    "project_event_counts": {"Kairos Apps": 75, "Gasco-Platform": 33},
    "selected_project_counts": {"Kairos Apps": 12, "Gasco-Platform": 8}
  }
}
```

Vì selection semantics và envelope thay đổi, tăng `CONTEXT_SCHEMA_VERSION` từ
`kairos.summary_context@1` lên `kairos.summary_context@2`.

Nếu số project lớn hơn số Event có thể chọn, policy phải ưu tiên deterministic và ghi project bị bỏ
vào metadata/omissions; không được tuyên bố coverage đầy đủ.

### 3.6 Project/evidence validator

Validator phải kiểm tra:

- `projects` là array và mỗi project chỉ xuất hiện một lần.
- Project tồn tại trong evidence index/context.
- Mỗi claim có ít nhất một E-ref.
- Mọi E-ref tồn tại và thuộc đúng project của claim.
- Claim không được trộn evidence của nhiều project.
- Project block không có claim có thể bị bỏ khi render, nhưng không được dùng để tạo project giả.

Ví dụ phải reject nếu `E010` thuộc `Gasco-Platform`:

```json
{
  "project": "Kairos Apps",
  "done": [{"text": "Đã kiểm tra Jaeger.", "evidence": ["E010"]}],
  "in_progress": [],
  "risks_or_notes": []
}
```

### 3.7 Renderer theo project

`render_summary_markdown()` phải:

- Render project trước, trạng thái sau.
- Dùng thứ tự project deterministic từ context, không tin thứ tự tùy ý của model.
- Không render section rỗng.
- Giữ citation E-ref sau từng claim.
- Render `omissions` cuối report.
- Không render project không có claim.

### 3.8 Prompt, repair và fallback

Trong `kairos/summary.py`:

- Cập nhật `_summary_output_contract()` sang schema `@2`.
- Nói rõ Event là untrusted data và không được trộn project.
- Yêu cầu model dùng đúng project name trong context.
- Repair prompt chỉ gửi output lỗi, lỗi validation và mapping tối thiểu
  `project → allowed E-refs`; không gửi lại toàn bộ event content.
- Chỉ repair một lần; vẫn sai thì fallback với `generation_error_code=invalid_output` và không cache.
- Fallback cũng nhóm sanitized Event theo project để report vẫn dùng được khi provider lỗi.

### 3.9 Output budget

Mức mặc định 1.200 ký tự có thể không đủ cho khoảng mười project. Giá trị khởi đầu đề xuất:

| Setting | Hiện tại | Đề xuất |
| --- | ---: | ---: |
| `summary_output_max_chars` | 1.200 | 4.000 |
| Minimum | 300 | 1.000 |
| Maximum | 12.000 | 12.000 |

Không âm thầm ghi đè cấu hình người dùng đã chỉnh. Migration/patch phải nêu rõ cách xử lý site đang
giữ giá trị mặc định cũ. Prompt nên giới hạn 1–3 claim quan trọng mỗi project và cho phép ghi project
không đủ dữ liệu vào `omissions`.

### 3.10 Cache và backward compatibility

`generation.py` đã đưa output schema version và output limit vào fingerprint. Khi tăng output/context
schema version:

- Generation mới tự cache miss và không dùng summary `@1`.
- Report cũ vẫn đọc/copy được; không rewrite `summary_text` lịch sử.
- Generate/Force Regenerate sẽ tạo output `@2`.
- Không cần field database mới trong C.5.3b nếu evidence index chưa được persist.
- C.5.4b sau này chịu trách nhiệm lưu validated JSON và manifest audit có retention.

## 5. Test matrix

### Context Builder

- Cùng title và khác project không bị deduplicate.
- Event thiếu project vào `Không xác định`.
- Mười project đều được đại diện khi budget đủ.
- Project lớn không chiếm hết budget.
- Kết quả không đổi khi đảo thứ tự input.
- Không vượt `max_events` hoặc `max_chars`.
- Metadata đếm đúng project gốc, project được chọn và project bị loại.

### Output validator

- Accept mười project với evidence hợp lệ.
- Reject project không có trong context.
- Reject project lặp.
- Reject evidence không tồn tại.
- Reject evidence thuộc project khác.
- Reject claim không có evidence.
- Reject field thừa/thiếu hoặc output vượt giới hạn.

### Integration và E2E

- Generate report nhóm đúng project.
- Renderer tạo đúng project/status headings.
- Invalid project/evidence được repair đúng một lần.
- Repair vẫn sai chuyển sang grouped fallback.
- Fallback không chứa raw payload, secret hoặc absolute path.
- Schema version mới làm cache miss; Force Regenerate vẫn hoạt động.
- Fixture có mười project, project trùng title, project rỗng, prompt injection và secret/path.

## 7. Gate hoàn thành

C.5.3b chỉ hoàn thành khi:

- Mười project xuất hiện thành nhóm độc lập nếu context budget đủ.
- 100% claim có ít nhất một evidence hợp lệ.
- 100% evidence của claim thuộc đúng project.
- Không deduplicate chéo project.
- Selection deterministic và có project fairness được test.
- Output/fallback không chứa raw payload, secret hoặc absolute path.
- Output sai chỉ repair tối đa một lần rồi fallback.
- Report cũ vẫn đọc được và cache cũ không bị tái sử dụng sai.
- Unit, integration và HTTP E2E tests đều pass.
